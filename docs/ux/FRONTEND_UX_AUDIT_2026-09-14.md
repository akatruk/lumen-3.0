# Lumen — аудит frontend, UX и UI

Дата: 14 сентября 2026. Объект: текущий lumen-rebuild / lumen-fix.

## Вывод

У Lumen есть цельный визуальный стиль, но интерфейс пока не соответствует зрелому инструменту видеоредактора. Основная слабость — организация принятия решений: трудно выбрать исходник внутри сервиса, понять конкретный план изменений, оценить расход до запуска и сравнить результат с оригиналом. Спокойная палитра и аккуратные карточки этого не компенсируют.

Наиболее полезное направление — построить интерфейс вокруг последовательности **найти → посмотреть → задать цель → оценить план → создать → сравнить → скачать**. Сохранить узнаваемую тёмно-зелёную идентичность; переработать приоритеты контента и состояния приложения.

Этот документ — аудит, не отчёт о внедрении редизайна. Production-код в рамках данного аудита не изменялся.

## Метод и границы проверки

- Просмотрен production-экран входа.
- Внутренние экраны проверены в браузере на локальном стенде с тем же frontend и сохранённым реальным QA-проектом: студия, выдача Douyin, импорт, библиотека, редактор, настройки.
- Для поиска использовался сохранённый настоящий ответ TikHub. Он пригоден для проверки интерфейса, но не доказывает актуальность выдачи или работу фильтров внешнего провайдера.
- Проверены DOM, вычисленные стили, компоненты React, локализация и CSS.
- Компоновка 390 px (редактор) и 320 px (студия) просмотрена в iframe на отдельном локальном QA-стенде. Это responsive-проверка Chromium, не тест реального iOS/Android, экранной клавиатуры или Safari. Ослабление frame-заголовков выполнено только в этом QA-процессе.
- Использован результат предыдущего технического аудита для понимания серверных ограничений. В этом аудите новые платные AI-монтажи не запускались.
- Интервью, аналитика поведения, screen-reader тестирование и сравнительные исследования конкурентов не проводились. Влияние на конверсию и время работы — гипотезы, не измеренные результаты.

Обозначения: **наблюдение** — воспроизведено в браузере; **код** — подтверждено реализацией; **оценка** — экспертное UX-суждение. P1 — исправить до расширения пользовательского тестирования; P2 — следующий цикл; P3 — развитие.

## Что уже стоит сохранить

- Узнаваемые логотип, тёмная боковая панель и спокойная зелёная палитра.
- Хорошо различимые основные кнопки на светлом фоне и сравнительно небольшое количество пунктов навигации.
- Привязка рекомендаций и транскрипта к таймкодам, переход к исходному моменту.
- Отдельные режимы исходника и результата; пользователь не теряет оригинал.
- Нативные dialog/details/video, видимый focus-outline, обработка prefers-reduced-motion.
- EN/简体中文, смена источника обучающего видео вместе с языком, локализованные даты.
- Разделение технической проверки и AI-оценки, оговорка об ограничениях AI.
- Блокирование повторного запуска во время обработки, подтверждение удаления, ограничение бюджета.

## Приоритетные проблемы

### P1-01. Сценарий создания проекта противоречит основному продукту

**Наблюдение + код.** Вверху студии находится поиск Douyin. Однако кнопки «New project» в sidebar и библиотеке открывают загрузку файла. Ниже поиска расположен второй большой hero с upload; обучение также начинается с Upload. Пользователь, пришедший улучшить найденный Douyin-ролик, не получает единого маршрута.

**Изменение:** единая точка «Создать проект»: основной вариант «Найти в Douyin», вторичный «Загрузить файл». Главный экран — поиск и продолжение работы; объясняющий hero и три рекламные карточки свернуть в onboarding. Обновить оба обучающих ролика после согласования окончательного flow.

**Готово, когда:** все CTA создания ведут к одной модели выбора источника; повторный пользователь видит поиск и недавние проекты без прокрутки через рекламные блоки.

Доказательство: `frontend/src/main.tsx:196`, `:246`, `:396`, `:512`, `:697`.

### P1-02. Выбрать видео предлагают до просмотра внутри Lumen

**Наблюдение + код.** В выдаче доступны обложка, заголовок, автор, длительность, лайки и «Improve this video». Видео не проигрывается. Для просмотра нужно уйти в Douyin; import-dialog тоже не содержит preview. Портретные обложки обрезаются в 4:3 через object-fit:cover — на скриншоте обрезан текст.

**Изменение:** карточка → preview с плеером, автором, полной подписью и явной кнопкой «Использовать это видео». Сохранять портретный характер кадров или показывать полный постер с нейтральными полями. Скачивание предпросмотра не должно незаметно запускать платный анализ.

**Готово, когда:** пользователь может уверенно просмотреть и отвергнуть исходник, не покидая выдачу и не создавая проект.

Зависимость: потребуется безопасная серверная выдача preview; одного изменения карточки недостаточно. Доказательство: `frontend/src/DouyinSearch.tsx:21`, `:28`; `frontend/src/style.css:2831`.

### P1-03. Бюджет не объясняет стоимость следующего решения

**Наблюдение + код.** Import показывает общий бюджет $3 и разрешение AI-вставок; редактор повторяет общий лимит. Не видно, сколько осталось и помещается ли текущий выбор. При 0 выбранных рекомендаций кнопка создания активна. Для original-формата такой запуск может не дать содержательного изменения, но пройти обработку и платную QA. При смене формата пустой набор может быть осмысленным — этот случай нужно объяснять отдельно.

**Изменение:** перед запуском показывать список изменений, доступный остаток, оценку/резерв расходов с пометкой о неопределённости. Блокировать бессодержательный запуск или явно назвать действие «Экспортировать без изменений». Не выдавать общий лимит за оценку стоимости. TikHub и OpenRouter учитывать раздельно.

**Готово, когда:** перед подтверждением пользователь может ответить «что изменится, сколько может стоить, хватит ли бюджета».

Доказательство: `frontend/src/main.tsx:1448`, `:1459`; `frontend/src/DouyinSearch.tsx:28`.

### P1-04. Маленький и бледный текст в зоне принятия решений

**Наблюдение + расчёт.** На desktop в редакторе: таймкоды, confidence и бюджет — 8 px; вкладки — 10 px. Вычисленные цвета и CSS дают следующие отношения контраста:

| Элемент | Цвет / фон | Контраст |
|---|---|---:|
| Неактивная, но доступная вкладка | #95a18b / #fbfcf9 | ≈2.63:1 |
| Бюджет в панели действия | #a0ad90 / #f5f8ee | ≈2.20:1 |
| Таймкод | #80916d / #f8faf4 | ≈3.23:1 |
| Confidence на белой карточке | #758469 / #ffffff | ≈3.99:1 |

Для обычного информационного текста WCAG AA предусматривает 4.5:1. Неактивная вкладка здесь не disabled: исключение для недоступных элементов к ней не относится. Это выборочная проверка, а не полная сертификация доступности. [W3C: Contrast Minimum](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html).

**Изменение:** основной UI-текст 14–16 px, вторичный преимущественно 12–14 px; увеличить насыщенность информационного текста. Уменьшать число элементов на строке вместо уменьшения шрифта при 941–1150 px.

**Готово, когда:** все информационные состояния проходят проверку контраста, таймкоды и вкладки читаются без масштабирования.

Доказательство: `frontend/src/style.css:1538`, `:1731`, `:2232`; измерения browser computed styles.

### P1-05. Мобильная версия складывает desktop-колонки, но не меняет приоритеты

**Наблюдение + код.** При 390 px длинный Douyin-заголовок с хэштегами занимает несколько строк в узкой левой части шапки; справа зарезервировано место под download/delete. Ниже располагаются видео, timeline, QA и brief; только затем рекомендации. Основное решение далеко от источника. На 320 px блок поиска почти заполняет первый экран.

**Изменение:** короткое редактируемое название, раскрываемая исходная подпись, компактная шапка. В mobile-проекте порядок: preview → следующий шаг/рекомендации → подробный анализ → QA/brief. Предусмотреть быстрый возврат к плееру и понятное закреплённое действие. Не прятать важный контент уменьшением до 8–10 px.

**Готово, когда:** на 360/390 px пользователь видит следующий шаг рядом с плеером; длинная подпись не определяет высоту всей шапки.

Доказательство: `frontend/src/main.tsx:1137`, `:1168`, `:1300`, `:1343`, `:1364`; `frontend/src/style.css:2383`, `:2445`.

### P1-06. Потеря контекста поиска

**Воспроизведено.** Поиск «咖啡» → 12 результатов → библиотека → студия: поле пустое, результатов нет. Поиск хранится только в локальном состоянии размонтируемого компонента. Refresh имеет тот же результат.

**Изменение:** хранить параметры поиска в URL, выдачу/пагинацию и позицию возврата в cache уровня приложения. Показывать истечение результатов с повторением того же запроса.

**Готово, когда:** из preview/проекта/библиотеки можно вернуться к той же выдаче и позиции.

Доказательство: `frontend/src/DouyinSearch.tsx:9`, `frontend/src/main.tsx:363`.

### P1-07. Ошибка проекта превращается в бесконечную загрузку

**Наблюдение + код.** Переход на отсутствующий project-id оставляет экран «Loading your workspace…». Ошибка попадает в глобальный баннер, но терминального состояния not-found нет. Успешный refresh списка проектов очищает общий error каждые 7 секунд, поэтому ошибка конкретного проекта может исчезать. Истечение сессии тоже не переводит приложение в понятный повторный вход: `/session` читается только при старте.

**Изменение:** независимые состояния session/list/detail; явные loading/not-found/forbidden/offline/error. На 401 — безопасный повторный вход с сохранением маршрута; на 404 — библиотека и действие возврата. Общая успешная загрузка не должна стирать ошибку другого запроса.

**Готово, когда:** отсутствующий проект не показывает бесконечный loader; network error отличается от отсутствия доступа; восстановление понятно без refresh страницы.

Доказательство: `frontend/src/main.tsx:145`, `:154`, `:170`, `:343`.

### P1-08. Результат трудно сравнить с исходником

**Код + наблюдение.** Переключение Original/New cut перемонтирует video и сбрасывает позицию. В режиме результата source timeline показывает 00:00; его нажатие возвращает в исходник. После появления результата default-режим остаётся source. Нет списка версий, а число «1 changes applied» не говорит, что именно было применено, пока пользователь не изучит детали проекта.

**Изменение:** отдельный экран/режим review с явным списком фактических изменений, длительностью до/после и сопоставлением по сохранённому монтажному timeline. Синхронизация не должна наивно использовать одинаковую секунду после вырезаний. «Посмотреть результат» — главное действие после завершения; скачивание — следующее.

**Готово, когда:** пользователь может проверить конкретную рекомендацию до/после и понимает, какую версию скачивает.

Зависимость: полноценная история версий требует расширения API/модели данных. Доказательство: `frontend/src/main.tsx:1043`, `:1203`, `:1229`, `:1334`.

## Frontend: технические причины UX-проблем

1. **Один main.tsx на 1690 строк.** Auth, layout, routing, upload, library, editor, settings и API-обвязка связаны состояниями одного дерева. Это само по себе не дефект для пользователя, но уже проявилось в общем error и потере контекста.
2. **Два API-клиента.** `api()` и локальный `post()` по-разному трактуют ошибки. Нужен единый typed error с HTTP status, domain code и действиями восстановления. Не отображать сырой backend-код пользователю.
3. **Polling без жизненного цикла.** Detail каждые 3.5 с, library каждые 7 с даже для завершённого проекта. Нет AbortController, остановки при hidden/offline, ограничения перекрывающихся запросов. Потенциально устаревший ответ может затереть более свежий. Это риск по коду, не воспроизведённая гонка в этом аудите.
4. **Routing не отделён от данных.** ProjectView не keyed по проекту; при некоторых переходах history до получения ответа могут сохраняться старые view-state. Нужна проверка A→B через Back/Forward с двумя проектами и раздельный state по id.
5. **CSS на 2857 строк с повторными переопределениями.** Адаптивные правила уменьшают функциональный текст, а финальные правила снова переопределяют размеры/цвета. Нужны tokens и компоненты, а не ещё один слой override.
6. **DouyinSearch фактически сжат в 29 длинных строк.** Это не влияет на runtime само по себе, но затрудняет review, доступность и сопровождение; отдельная локализация усиливает расхождения.
7. **Нет frontend-test scripts.** Backend-тесты не ловят потерю поиска, ошибку маршрута, мобильную шапку или keyboard-navigation. В package.json есть dev/build/preview, но нет автоматизированного UX regression suite.
8. **Скачивание через blob.** Весь файл сначала читается в память браузера, прогресс не показан (`main.tsx:1108`). Для больших output предпочтителен серверный attachment/download URL с сохранением авторизации; измерить на слабом мобильном устройстве.
9. **Видео не имеет прикладного error-state.** У плеера проекта отсутствует onError с понятной повторной загрузкой. Отказ медиа/истечение сессии не должен выглядеть как просто чёрный экран.

Предлагаемое разделение: `app` (router/session/layout), `features/discovery`, `features/project-create`, `features/editor`, `features/library`, `features/review`, `shared/api`, `shared/ui`, `locales`. Это направление рефакторинга, не требование вводить множество новых библиотек.

## Целевая структура интерфейса

**Навигация:** «Найти видео», «Проекты», «Настройки». Один CTA создания с выбором Douyin/файл.

**Поиск:** компактная строка → явно применённые фильтры → выдача → preview выбранного видео. После возврата сохраняются запрос, фильтры и позиция.

**Создание:** выбранный источник → цель → параметры. Advanced: формат, авто-монтаж, AI-вставки, расходы. Язык интерфейса и язык субтитров названы отдельно.

**Анализ:** preview и реальные стадии обработки. После готовности — 2–3 главных наблюдения, рекомендации с конкретными действиями. Никакого обязательного просмотра всех оценок перед первым решением.

**Монтаж:** явный список выбранных операций, продолжительность и стоимость/резерв. Для генерации — отдельная понятная маркировка.

**Review:** новая версия, список фактических изменений, сравнение с исходником, техническая QA и AI-замечания, download. При QA-unavailable результат остаётся доступен с соответствующим статусом.

**Mobile:** краткая шапка → видео → следующий шаг → детали по раскрытию. Проверка не только 390 px, но 320/360/768/1024, EN/中文 и длинных текстов.

## Визуальная система для следующей итерации

- Сохранить pine/lime как узнаваемые акценты. Основной текст сделать темнее, вторичный — читаемым, а не почти декоративным.
- Выделить tokens для background/surface/text/muted/border/action/positive/warning/error; не смешивать «выбрано» и «прошло QA» только зелёным цветом.
- Основной текст 14–16 px; labels 13–14; metadata преимущественно 12–13. Мелкие декоративные overline не должны содержать необходимую для решения информацию.
- Кнопки touch-действий проектировать около 44 px по высоте; это дизайн-цель удобства, не утверждение, что всякая меньшая кнопка автоматически нарушает WCAG.
- Радиусы и отступы свести к небольшой шкале. Белая/нейтральная рабочая зона должна поддерживать видео, а не конкурировать с ним.
- Китайскому тексту дать отдельную проверку line-height, переносов и плотности. Длинную подпись хранить отдельно от рабочего названия.

## Порядок внедрения и проверка результата

### Цикл 1 — устранить препятствия

P1-03/04/06/07: понятный платный запуск, читаемость, сохранение поиска, нормальные error/session states. Включить F03, A01/A02. Это можно в основном сделать без изменения AI-пайплайна.

### Цикл 2 — перестроить основной путь

Единый вход в создание, preview исходника, общая форма, mobile editor, новые состояния auto-render. Здесь потребуется серверная поддержка безопасного preview и редактирования параметров.

### Цикл 3 — доказать ценность результата

Сравнение до/после, история версий, исправление транскрипта, прозрачный учёт стоимости. Обновить обучение после стабилизации сценария.
